Most databases that need a migration tool already exist. There are two commands for that case and
they answer different questions.

| You have | You need | Command |
|---|---|---|
| a database **and** a schema file that already describes it | a start of history | `migrate baseline` |
| a database and no schema file | a schema file | `pull`, then `migrate baseline` |

Neither command executes DDL against your database. `baseline` records a migration without running
it; `pull` reads the catalog and writes files. Adoption is a repository change, not a database
change.

## `migrate baseline`

`baseline` introspects the live database, writes `0000_baseline.sql` and its `.plan.json` holding
the whole current schema as DDL, and inserts a history row marked `baselined` — **without executing
the file**. The objects are already there; what was missing was the record that says so.

```sh
pg-prime migrate baseline
```

```text frame="terminal"
migrate baseline
  wrote        …/migrations/0000_baseline.sql
  plan         …/migrations/0000_baseline.plan.json
  statements   12
  fingerprint  sha256:57e7326184bb1fc8ded4659a1d43a92f8a71a74370842c82eb3a67e57a28cae5
  history      0000_baseline recorded as baselined; nothing was executed
```

The file is a real migration, built by the ordinary create path rather than by a special one:

```sql title="migrations/0000_baseline.sql (excerpt)"
-- pg-prime:migration 0000_baseline
-- pg-prime:plan      0000_baseline.plan.json
-- pg-prime:from      sha256:bcb83d0e69a2603084b68c868f2ae1ffa396f30223c9b258bb6606bfa4008926
-- pg-prime:to        sha256:57e7326184bb1fc8ded4659a1d43a92f8a71a74370842c82eb3a67e57a28cae5
-- pg-prime:txmode    transactional
-- pg-prime:timeout   lock=3s statement=per-statement
-- pg-prime:requires-pg 150000

SET search_path = pg_catalog;

-- pg-prime:segment 0 transactional
-- pg-prime:stmt 0 lock=none idempotent
CREATE SEQUENCE IF NOT EXISTS "public"."customer_customer_id_seq" AS integer INCREMENT BY 1 MINVALUE 1 MAXVALUE 2147483647 START WITH 1 CACHE 1 NO CYCLE;

-- … the second sequence …

-- pg-prime:stmt 2 lock=none non-idempotent
CREATE TABLE "public"."customer" (
  "customer_id" integer DEFAULT nextval('public.customer_customer_id_seq'::regclass) NOT NULL,
  "first_name" character varying(45) NOT NULL,
  …
```

That it is a real file matters: `migrate verify` can replay a baselined repository from empty like
any other, so "the repository reproduces this database" is a claim you can check rather than one
you have to believe.

The `fingerprint_to` on the recorded row is the live fingerprint, which is what makes the next
`apply`'s fast-path gate work on an adopted database.

`--at <id>` does the other adoption: a directory that **another tool** already applied. It marks
every file up to and including `<id>` as `baselined` and executes none of them — the equivalent of
Prisma's `migrate resolve --applied`. Marking only the named file would leave its predecessors
pending and `apply` would run them, so the whole prefix is taken.

`baseline` refuses when `pgprime.migrations` is not empty, because it rewrites the start of
history:

```text frame="terminal"
migrate baseline

REFUSED: 1 row already exists in pgprime.migrations (0000_baseline). baseline rewrites the start of history; pass --force if that is what you mean.
```

**Exit: 0** · **1**.

## `pull`

`pull` introspects the database and writes a deterministic TypeScript schema file, plus a `sql/`
tree of repeatables for everything the schema DSL does not model.

```sh
pg-prime pull
```

```text frame="terminal"
pull — docs_legacy (public)
  wrote        …/db/schema.ts
  report       …/db/pull.report.json
  repeatables  3 files under …/sql
  objects      2 sequence, 2 table

1 object the DSL cannot express (also in pull.report.json):
  - expression index  public.idx_customer_lower_email  — the DSL has no expression-index spelling: lower(email)
Next: point `schema` in pg-prime.config.ts at db/schema.ts and run `pg-prime migrate baseline`, then `pg-prime migrate generate` to see an empty diff.
```

`--out <file>` picks where the TypeScript goes (default `./db/schema.ts`); the report is written
beside it. `--sql-dir <dir>` picks where the repeatables go (default the config's `repeatables`, or
`./sql`), `--no-sql-dir` reports every Tier-R object as unsupported instead of writing it, and
`--dry-run` prints the TypeScript and writes nothing.

**Exit: 0** written · **1** error.

### What it emits

```ts title="db/schema.ts" no-run="what pg-prime pull writes: a generated schema module, shown as it lands on disk"
/**
 * Generated by `pg-prime pull` — design/06 §6.2.
 *
 * Managed schemas: public.
 * 3 Tier-R object(s) — views, functions, triggers, policies,
 * matviews, aggregates — were written to `sql/` as repeatables instead:
 * they are re-applied by hash rather than diffed (design/06 §3.8).
 *
 * This file is meant to be edited. It is the DSL's spelling of what the database
 * currently contains, so `pg-prime migrate generate` against that same database
 * reports an empty diff until you change something.
 */

// -- pull: unsupported
//
// The database contains objects this DSL cannot express. They are NOT in the schema
// below, so `migrate generate` against this file would plan to DROP them. Keep them out
// of the managed schema set, or write them by hand in a migration, until the DSL grows
// the spelling. The same list is in pull.report.json. (1 object(s).)
//   expression index  public.idx_customer_lower_email  — the DSL has no expression-index spelling: lower(email)
// -- end pull: unsupported

import { comment, defineSchema, foreignKey, index, pgSequence, pgTable, primaryKey } from 'pg-prime/schema'
import type { RefLike } from 'pg-prime/schema'

export const customerCustomerIdSeq = pgSequence("customer_customer_id_seq", { dataType: "integer", start: "1", increment: "1", minValue: "1", maxValue: "2147483647", cache: "1", ownedBy: { table: "customer", column: "customer_id" } })
export const rentalRentalIdSeq = pgSequence("rental_rental_id_seq", { dataType: "integer", start: "1", increment: "1", minValue: "1", maxValue: "2147483647", cache: "1", ownedBy: { table: "rental", column: "rental_id" } })

export const customer = pgTable("customer", (t) => ({
  customerId: t.integer("customer_id").defaultSql("nextval('public.customer_customer_id_seq'::regclass)"),
  firstName: t.raw("character varying(45)", "first_name"),
  lastName: t.raw("character varying(45)", "last_name"),
  email: t.text("email").nullable(),
  activebool: t.boolean("activebool").defaultSql("true"),
}), (t) => [
  comment("One row per customer."),
  primaryKey({ name: "customer_pkey", columns: [t.customerId] }),
])

export const rental = pgTable("rental", (t) => ({
  rentalId: t.integer("rental_id").defaultSql("nextval('public.rental_rental_id_seq'::regclass)"),
  customerId: t.integer("customer_id"),
  rentedAt: t.timestamptz("rented_at").defaultSql("now()"),
  returnedAt: t.timestamptz("returned_at").nullable(),
}), (t) => [
  primaryKey({ name: "rental_pkey", columns: [t.rentalId] }),
  foreignKey({ name: "rental_customer_id_fkey", columns: [t.customerId], references: (): readonly RefLike[] => [customer.cols.customerId], onDelete: "restrict" }),
  index("idx_rental_customer").on(t.customerId),
])

export default defineSchema({
  customer,
  rental,
})
```

Four things in that file are deliberate.

- **Every column carries its database name as an argument** — `t.raw('character varying(45)',
  'first_name')`, not `firstName: t.raw(…)` and a casing strategy. The TypeScript key is an alias
  `pull` invented; the database name is data.
- **The type mapping is an exact-match table and nothing else.** `format_type` output that is not
  one of eleven known strings becomes `t.raw('<the exact text>')`, which the emitter writes
  verbatim and PostgreSQL parses back to the same type. Guessing that `character varying(45)` is
  "a varchar, near enough" is how a pull silently drops a length limit.
- **The import is `pg-prime/schema`**, and `pg-prime/sql` alongside it when a `CHECK` or a partial
  index needs `sql.unsafeRaw`. Both are documented public subpaths; the same names are on the root
  too, and keeping the generated file off the root barrel keeps its import graph small.
- **The foreign key's thunk states its return type.** `references: (): readonly RefLike[] => …` is
  what a mutually referencing pair needs to avoid `TS7024`, and stating it always costs one import
  and never has to be reasoned about. A self-reference is written against the extras callback's own
  parameter instead, because naming the table's own `const` inside its initializer is `TS7022`.

Beyond tables and columns, `pull` emits enums, domains, sequences, extensions, comments, indexes
(with `using`, `where`, `include`, `nullsNotDistinct` and per-column `desc`/`nulls`/`opclass`),
constraints, and partitions. Tables come out in **foreign-key dependency order**, ties broken by
name; columns come out in `attnum` order, which is observable through `pg_dump` and therefore
semantic; everything else is sorted on a property of the schema rather than of the extraction.

A partition child is emitted as a plain `CREATE TABLE` plus `ALTER TABLE parent ATTACH PARTITION`,
not as `CREATE TABLE … PARTITION OF`. `PARTITION OF` clones the parent's constraints *with their
names*, and PostgreSQL 18 catalogues `NOT NULL` as a named `pg_constraint` row, so the next
`generate` would plan a rename of an inherited constraint — which PostgreSQL refuses. `pg_dump`
uses the same two-step form.

### The `sql/` tree

Functions, views, materialized views, triggers, policies and aggregates are Tier R: re-applied from
`sql/` by hash rather than diffed. `pull` writes them there, in a directory-lexicographic order the
runner replays:

```
sql/
  000_prelude.sql
  010_functions/public__customer_name__c_customer.sql
  020_views/public__active_customer.sql
```

Every statement it writes is idempotent, because a repeatable that is not gets refused by `TX201` —
a repeatable is re-applied on every deploy whose bytes changed, and a bare `CREATE TRIGGER` wedges
the second one.

`000_prelude.sql` appears whenever the schema has functions:

```sql title="sql/000_prelude.sql"
-- pg-prime:object prelude check_function_bodies
-- Written by `pg-prime pull`. Functions below are applied in directory order, and a
-- LANGUAGE sql body is parsed at CREATE time, so one that calls another would fail on
-- the alphabet. `pg_dump` emits exactly this line in its preamble for the same reason.
SET check_function_bodies = false;
```

A `LANGUAGE sql` body is parsed when the function is created, so a function that calls another
cannot be created before it — and for a non-atomic SQL body the call graph is not in `pg_depend`,
so there is no order to sort them into. `pg_dump` solves it the same way.

Views get their **real** `securityInvoker` written out explicitly, with a comment naming the
default they would otherwise get:

```sql title="sql/020_views/public__active_customer.sql"
-- pg-prime:object view public.active_customer
-- security_invoker = false — PostgreSQL's own default, and what this database has.
-- design/00 decision 5 makes `true` the default for a view pg-prime CREATES; pull writes
-- the real value rather than changing who this view's RLS is evaluated as.
CREATE OR REPLACE VIEW "public"."active_customer" WITH (security_invoker = false) AS
 SELECT customer_id,
    first_name,
    last_name
   FROM customer
  WHERE activebool;
```

Silently rewriting a legacy view to `security_invoker = true` would change who its row-level
security policies are evaluated as — a security change, made by a tool, without being asked.

Extension-owned objects are excluded everywhere, exactly as the extractor excludes them from the
fact base: they belong to the extension, `CREATE EXTENSION` brings them back, and writing them into
`sql/` would make your repository claim to own `uuid_generate_v1()`.

### A second `pull` is byte-identical

Every list in the emitted file is sorted on something that is a property of the schema, never of
the extraction. So running `pull` twice over the same database produces the same bytes, and `pull`
over a database built from a pulled schema produces the same file again. That is a property you can
check in CI, and it is what makes the file safe to re-take rather than something you have to
hand-merge.

Unlike a migration, a pulled file is **overwritten** on purpose: a migration is immutable history,
and a pulled schema is a snapshot you re-take. The round-trip property is only checkable if the
second run is allowed to write.

## The `-- pull: unsupported` block

`pull` is a **recogniser, not a SQL parser**. Everything it reads back — `pg_get_constraintdef`,
`pg_get_indexdef` — is recognised with certainty or not at all, and a "not at all" becomes a line
in the header block and an entry in `pull.report.json`:

```json title="db/pull.report.json (excerpt)"
{
  "unsupported": [
    {
      "kind": "expression index",
      "name": "public.idx_customer_lower_email",
      "reason": "the DSL has no expression-index spelling: lower(email)"
    }
  ]
}
```

The asymmetry is the whole design. A parser that guesses produces a schema file which *looks* right
and emits a migration that quietly changes a constraint; a recogniser that gives up produces a gap
somebody can see. The block is part of the emitted file rather than only in the report, because the
file is the thing a reviewer reads.

What `pull` cannot express today, each with an exact reason string:

| Shape | Why |
|---|---|
| expression indexes | the DSL has no expression-index spelling |
| `WITH (…)` or `TABLESPACE` on an index | the DSL cannot say either, and an index whose `fillfactor` was dropped is a different index |
| `EXCLUDE` constraints | no DSL spelling |
| `NOT VALID` constraints | the DSL has no `.notValid()` |
| composite types | there is no `pgCompositeType` |
| generated columns | the DSL has no `.generatedAlwaysAs()` |
| column collations | the DSL has no `.collate()` |
| unlogged tables | the DSL has no `unlogged()` |

<Aside type="note">
**None of them appears in the four corpus schemas.** chinook, northwind, adventureworks and pagila
all round-trip through `pull` to an **empty** `migrate generate` and an **empty** unsupported
block — including adventureworks' eleven schemas, 68 tables and 93 repeatables, and pagila's
range-partitioned parent with seven children. That is the measured bar this feature is held to, not
an aspiration.
</Aside>

An entry in the block is a standing diff, and the file says so: those objects are not in the schema
below, so `generate` will plan to **drop** them. That is exactly what happens if you adopt without
reading the block:

```sql title="migrations/0001_adopt_check.sql (excerpt)"
-- pg-prime:stmt 0 lock=accessExclusive idempotent hazards=LK102
DROP INDEX IF EXISTS "public"."idx_customer_lower_email";
```

Move the object out of the managed schema set, or keep it and accept that `generate` will keep
offering to drop it, until the DSL grows the spelling.

## The recommended order

<Steps>

1. **`pull`**, into a branch of its own, with `--out` pointing where your schema lives.

   ```sh
   pg-prime pull --out ./src/schema.ts --sql-dir ./sql
   ```

2. **Read the unsupported block first.** It is at the top of the file and it is the only part of
   the output that says something is missing. If it is empty, the rest of the adoption is
   mechanical.

3. **Review the schema file as code.** The identifiers are `pull`'s guesses at names — `activebool`
   is what the column is called, and you may want the TypeScript key to read better. Renaming a
   *key* is free: the database name is the argument, and it is what the diff uses.

4. **Point the config at it.**

   ```ts title="pg-prime.config.ts" no-run="a config file: the kit loads it, and as a program it executes nothing"
   import { defineConfig } from '@pg-prime/kit'

   export default defineConfig({
     schema: './src/schema.ts',
     migrations: './migrations',
     repeatables: './sql',
     url: process.env['DATABASE_URL']!,
   })
   ```

5. **`migrate baseline`.** One file, one history row, nothing executed.

6. **`migrate generate` — and expect it to write nothing.** This is the acceptance test for the
   whole adoption:

   ```sh
   pg-prime migrate generate --name adopt_check
   ```

   ```text frame="terminal"
   migrate generate — docs_legacy (shadow tier 2: the admin role has CREATEDB)

   nothing to do — the database already matches the schema.
   ```

   An empty diff means the round trip closed: your TypeScript, loaded into a shadow database and
   normalized by PostgreSQL, produces the same catalog you started from. Anything else is a real
   difference, and the statements it wants to write name it exactly.

</Steps>

From here the loop is the ordinary one: change the schema, `generate`, review, `apply`.

## Two things to check before you start

- **`pull` on shadow tier 3 is untested.** The round-trip corpus runs on tier 2, where the role has
  `CREATEDB`. If your adoption target is a managed PostgreSQL with a restricted role, expect the
  `pull` → `generate` path to work and verify the empty diff yourself rather than assuming it.
- **`pull` reads only the schemas you name.** Its default is `public`; pass `--schema` for each
  additional one, and remember that the managed set is also the scope of the diff, of the
  fingerprint and of the advisory lock. A foreign key pointing at a table outside the set becomes
  an unsupported entry rather than a silent omission.
