`@pg-prime/kit` ships one binary and one entry point. **Most people who use the kit never import
from it**: the thirteen commands documented in [the CLI reference](/pg-prime/reference/cli/) are the
interface, and [migrations end to end](/pg-prime/guides/migrations/) is the guide that explains what
each one is for.

Everything below is the **programmatic API** — the engine the binary is built out of, exported so
that something else can drive it. The shapes that need it are a test harness that generates and
applies a migration in-process, a platform's own deploy tool that wants `applyPending`'s event
stream rather than its stdout, and a script that reads a `.plan.json` off disk and lints it. If you
are not writing one of those, the CLI page is the page you want.

```sh
pnpm add -D @pg-prime/kit
```

```ts
import { applyPending, buildPlan, diffIR, extractCatalog, generate } from '@pg-prime/kit'
```

<Aside>
There is exactly one entry point, `@pg-prime/kit`. There are no subpaths: the 321 names below all
come from the same import, and the package's `exports` map has nothing else in it. `pg-prime` is a
**peer** dependency, imported for types only — the kit never loads the runtime package at run time.
</Aside>

## The pipeline

The names group by the stage of the pipeline they belong to, and the pipeline is short:

```text
pg_catalog ──extract──► SchemaIR ──diff──► Delta[] ──build──► Statement[] ──order──► Plan
     ▲                     ▲                                                          │
     │                     │                                                       prove
 the target        the desired state,                                                 │
                normalised through a shadow                                           ▼
                                                            NNNN_name.sql + NNNN_name.plan.json
```

Read left to right for `migrate generate`; the runner (`applyPending`) picks the artifacts up on
disk and never repeats any of it. The three commands that write nothing — `status`, `check`,
`doctor` — are the same functions with the write step removed.

| If you want to | Start at |
|---|---|
| read a config file the way the CLI does | [`loadConfig`](#loadconfig), [`resolveConfig`](#resolveconfig) |
| turn a live database into an IR | [`extractCatalog`](#extractcatalog) |
| turn a TypeScript schema into an IR | [`loadDesired`](#loaddesired), [`provisionShadow`](#provisionshadow) |
| produce a migration end to end | [`generate`](#generate) |
| apply what is on disk | [`applyPending`](#applypending) |
| report without writing | [`migrationStatus`](#migrationstatus), [`lintPlan`](#lintplan) |
| break a lease left by a dead deploy | [`inspectLease`](#inspectlease), [`forceUnlock`](#forceunlock) |

`migrate checkpoint`, `db seed` and `pull` are **CLI-only** in this release: they exist as commands,
their behaviour is documented on the CLI page, and none of their functions are exported here. Nothing
below can write a checkpoint or run a seed.

## Configuration

The config leg is three steps kept apart on purpose: find the file, import and validate it, then
fold in the command line and the environment. A caller that only wants the last step can build a
`PgPrimeConfig` object itself and never touch a file.

### `loadConfig`

{/* docs: signature */}
```ts
function loadConfig(path?: string, cwd?: string): Promise<LoadedConfig>
```

Imports the config module and hands back its default export beside the path it came from. With no
`path` it searches `CONFIG_FILENAMES` at and above `cwd`; with no config file anywhere it returns
`{ file: null, config: {} }`, because an absent config is a valid state and only an unreadable one is
an error. Every key is validated on the way out, so `migrations: 3` throws a `ConfigError` that names
the key rather than failing somewhere later with a path join.

### `findConfigFile`

{/* docs: signature */}
```ts
function findConfigFile(from: string): Promise<string | null>
```

The search on its own: the four `CONFIG_FILENAMES` in `from`, then in each ancestor directory, first
hit wins, `null` at the filesystem root.

### `resolveConfig`

{/* docs: signature */}
```ts
function resolveConfig(input: ResolveInput): ResolvedConfig
```

Folds the command line and the environment into a loaded config and resolves every path against the
config file's own directory. Precedence for the connection, highest first: `--url`,
`config.connection`, `config.url`, `PG_PRIME_DATABASE_URL`, `DATABASE_URL` — the project's file beats
the ambient environment, because a `DATABASE_URL` left over in a shell is the classic way to migrate
the wrong database. Pass `requireConnection: false` for a placeholder connection instead of a throw;
that is what makes `migrate lint <file>` a pure function of files.

### `defineConfig`

{/* docs: signature */}
```ts
function defineConfig(config: PgPrimeConfig): PgPrimeConfig
```

Identity at run time. It exists so `pg-prime.config.ts` gets completion and so a typo in a key is a
compile error in your editor rather than a setting that is silently ignored. Every key it accepts is
documented on [the config file reference](/pg-prime/reference/config/).

| Name | Shape | What it is |
|---|---|---|
| <a id="PgPrimeConfig"/> `PgPrimeConfig` | `{ url?, connection?, migrations?, repeatables?, schemas?, shadow?, schema?, replicas?, seeds?, … }` | Every key of `pg-prime.config.ts`. All optional. |
| <a id="LoadedConfig"/> `LoadedConfig` | `{ file: string \| null; config: PgPrimeConfig }` | What `loadConfig` returns: the validated object and the file it came from. |
| <a id="ResolveInput"/> `ResolveInput` | `{ config, configFile, cwd, env, url?, migrations?, schemas?, requireConnection? }` | `resolveConfig`'s argument — the config plus the CLI's global options. |
| <a id="ResolvedConfig"/> `ResolvedConfig` | `{ connection, hasConnection, migrationsDir, repeatablesDir, seedsDir, schemaPaths, schemas, replicas, env, production, warnings }` | Absolute paths and one `ConnInfo`. `hasConnection: false` means the connection is a placeholder and nothing may connect with it. |
| <a id="parseDatabaseUrl"/> `parseDatabaseUrl` | `(url: string) => ParsedUrl` | `postgres://user:pass@host:port/db` to a `ConnInfo`. Query parameters are **dropped and named** in `warnings`, because a silently ignored `sslmode=require` only shows up in production. |
| <a id="ParsedUrl"/> `ParsedUrl` | `{ conn: ConnInfo; warnings: readonly string[] }` | The parse, plus what it had to throw away. |
| <a id="loadSchema"/> `loadSchema` | `(paths: string \| readonly string[], base: string) => Promise<LoadedSchema>` | Imports the module(s) `config.schema` names and merges them into one registry. Accepts a `defineSchema` default export, any export with a `tables` property, or a module of bare `pgTable` exports. |
| <a id="LoadedSchema"/> `LoadedSchema` | `{ schema: { tables, enums, domains, sequences, extensions, schemas }; files }` | One registry, keyed by `schema.name` so a table exported twice under two names is still one table. |
| <a id="STRIP_TYPES_MARKER"/> `STRIP_TYPES_MARKER` | `"PG_PRIME_STRIP_TYPES_RETRY"` | Set by the CLI before it re-execs itself with `--experimental-strip-types`, so the retry can happen at most once. |

## Loading the desired state

The desired state is never diffed as text. It is emitted into a real PostgreSQL and read back out,
so that "what you wrote" and "what the catalog holds" are the same form by construction. That is the
whole reason the shadow ladder exists.

### `emitSchema`

{/* docs: signature */}
```ts
function emitSchema(schema: SchemaLike, options?: EmitOptions): EmitResult
```

Turns a `defineSchema(...)` registry into complete DDL statements in execution order, without
trailing semicolons. `schemaMap` renames every schema on the way out, which is how the temp-schema
tier puts a user's `public` somewhere it cannot collide; the emitter never touches `search_path`,
because emitted DDL is always schema-qualified and a GUC cannot disambiguate a cross-schema foreign
key.

### `loadDesired`

{/* docs: signature */}
```ts
function loadDesired(schema: SchemaLike, shadow: Shadow, options?: LoadDesiredOptions): Promise<ExtractResult>
```

Emit into the shadow, run the `afterLoad` hook, extract, and hand the IR back **in the caller's own
schema names**. The `afterLoad` hook is where Tier R goes: repeatables are loaded into the shadow
beside the desired schema, so a view that references a to-be-dropped column fails the proof at author
time rather than at deploy time. An `error`-severity emit diagnostic stops the load before a single
statement runs.

### `provisionShadow`

{/* docs: signature */}
```ts
function provisionShadow(admin: ConnInfo, target: ConnInfo, options: ProvisionShadowOptions): Promise<Shadow>
```

Picks a tier and hands back the connection, the schema map and a `dispose`. Tier 1 is a shadow URL
you supply, tier 2 is `CREATE DATABASE` with the target's locale copied, tier 3 is
`CREATE SCHEMA pgprime_shadow_<token>_<name>` **inside the target database** — which is why the
ladder never requires `CREATEDB`. Tier 4 (`offline`) throws `OfflineShadowError` with a sentence
explaining why it cannot exist; see [the shadow ladder](/pg-prime/concepts/shadow-ladder/).

| Name | Shape | What it is |
|---|---|---|
| <a id="desiredSql"/> `desiredSql` | `(schema: SchemaLike, shadow: Shadow, options?: LoadDesiredOptions) => readonly string[]` | The statements `loadDesired` would run, for `--dry-run` and for golden tests. |
| <a id="EmitOptions"/> `EmitOptions` | `{ schemaMap?: ReadonlyMap<string, string>; defaultSchema?: string }` | The rename map and where an unqualified table lands (`public`). |
| <a id="EmitResult"/> `EmitResult` | `{ sql: readonly string[]; diagnostics; schemas }` | Statements in execution order, plus the schemas they touch in the caller's names. |
| <a id="LoadDesiredOptions"/> `LoadDesiredOptions` | `{ defaultSchema?; statementTimeout?; afterLoad?: (client) => Promise<void> }` | `afterLoad` runs on the shadow's own connection, after the DDL and before the extract. |
| <a id="SchemaLike"/> `SchemaLike` | `{ tables; enums?; domains?; sequences?; extensions?; schemas? }` | A schema registry. `Schema<T, R>` from `pg-prime` is assignable to it, and so is a bare `{ tables }` literal. |
| <a id="TableLike"/> `TableLike` | `{ $: TableRuntime }` | One table as the registry holds it. |
| <a id="TableRuntime"/> `TableRuntime` | `{ name; schema; columns; extras; column(key) }` | The runtime metadata behind a table's `$`. Non-generic, so it costs nothing per instantiation. |
| <a id="RefRuntime"/> `RefRuntime` | `{ table; schema; key; dbName; column }` | A column reference's runtime metadata. Carries the schema so a cross-schema foreign key target is never guessed by table name. |
| <a id="ColumnDdl"/> `ColumnDdl` | `{ pgType; dbName; notNull; default; identity; primaryKey; unique; enumName; arrayDim; references; checks; comment; renamedFrom }` | Everything a column contributes to DDL. No `$`-prefixed builder method ever writes into it. |
| <a id="TableExtra"/> `TableExtra` | a tagged union: `primaryKey \| index \| comment \| unique \| check \| foreignKey \| renamedFrom \| clusterOn \| partitionBy \| partitionOf` | Table-level nodes, one heterogeneous array, extensible by extension packs without an API change. |
| <a id="makeRemapper"/> `makeRemapper` | `(reverse: ReadonlyMap<string, string>) => Remapper` | Builds the shadow-schema-to-user-schema rewriter. The quoted spelling is replaced first, so the bare rule cannot leave a stray quote behind. |
| <a id="Remapper"/> `Remapper` | `{ text: (s: string) => string; id: (id: StableId) => StableId }` | Rewrites every string in every payload, recursively. Safe by construction: the only token ever replaced is a shadow schema name, which was minted after the user's schema was written. |
| <a id="remapIr"/> `remapIr` | `(ir: SchemaIR, reverse: ReadonlyMap<string, string>) => SchemaIR` | A whole IR back into the caller's schema names. |
| <a id="remapObserved"/> `remapObserved` | `(observed: readonly ObservedObject[], reverse) => ObservedObject[]` | The same rename over Tier-O observations, which carry their identity as text. |
| <a id="remapDiagnostics"/> `remapDiagnostics` | `(diagnostics: readonly Diagnostic[], reverse) => Diagnostic[]` | So a message never names a schema the user has not got. |

## Catalog extraction

### `extractCatalog`

{/* docs: signature */}
```ts
function extractCatalog(client: CatalogClient, options?: ExtractOptions): Promise<ExtractResult>
```

Reads `pg_catalog` under one repeatable-read snapshot and returns the fact base, the server version,
the diagnostics and the Tier-O census. `CatalogClient` is one method — `query(text, values?)` — so
anything that can run SQL is an acceptable client, including a `pg.Client`, a pool checkout, or a
recording wrapper. Set `observe: false` to skip the Tier-O sweep and its sixteen round trips; the
shadow proof does, because it re-extracts twice per plan and never looks at observation.

| Name | Shape | What it is |
|---|---|---|
| <a id="CatalogClient"/> `CatalogClient` | `{ query(text: string, values?: unknown[]): Promise<{ rows: Record<string, unknown>[] }> }` | The one method the kit needs from a connection. |
| <a id="ExtractOptions"/> `ExtractOptions` | `{ schemas?; provenance?; statementTimeout?; observe? }` | Scope, stamp, timeout and the Tier-O switch. |
| <a id="ExtractResult"/> `ExtractResult` | `{ ir: SchemaIR; pgVersionNum: number; diagnostics; observed }` | `observed` travels **beside** the IR, never in it: a fact is diffed and hashed, so a `GRANT` in the fingerprint would read as schema drift. |
| <a id="Diagnostic"/> `Diagnostic` | `{ code; severity: "info" \| "warning" \| "error"; message; subject?; count? }` | Every report the kit produces, one shape. |
| <a id="ObservedObject"/> `ObservedObject` | `{ kind; name; detail }` | Roles, ACLs, publications, subscriptions, FDWs, event triggers, collations, aggregates — introspected and reported, **never diffed and never dropped**. |
| <a id="observedCounts"/> `observedCounts` | `(observed: readonly ObservedObject[]) => { kind: string; count: number }[]` | Per-kind counts for the `status` and `doctor` reports. |
| <a id="observationDiagnostics"/> `observationDiagnostics` | `(observed: readonly ObservedObject[]) => Diagnostic[]` | One `info` diagnostic per observed kind. |
| <a id="evaluatedEnumLabels"/> `evaluatedEnumLabels` | `(expr: string, enumLabels: ReadonlyMap<string, readonly string[]>) => StableId[]` | Which enum labels an expression evaluates at DDL time. Deliberately conservative: over-matching costs a redundant commit boundary, under-matching costs a failed migration. |
| <a id="probeEmptiness"/> `probeEmptiness` | `(client: CatalogClient, tables: readonly StableId[]) => Promise<Set<string>>` | The encoded table ids that are provably empty, by `SELECT EXISTS (SELECT 1 FROM t LIMIT 1)`. Used only to suppress an MF hazard, so "we do not know" is the safe answer and the one an unreachable target gives. |

## The IR

A fact's own name lives in its **id**, never in its hashed payload. Rename-as-hash-join, immunity to
phantom diffs, and dependency edges that land on real targets all follow from that one rule.

| Name | Shape | What it is |
|---|---|---|
| <a id="SchemaIR"/> `SchemaIR` | `class` with `build`, `facts`, `edges`, `get`, `has`, `childrenOf`, `descendantsOf`, `outgoingEdges`, `factsOfKind`, `contentHashOf`, `rollupOf`, `orphans`, `fingerprint`, `toCheckpoint` | The fact base. `fingerprint` is the sorted `(rootId, rollup)` pairs — the number `apply` gates on. |
| <a id="Fact"/> `Fact` | `{ id: StableId; parent?: StableId; payload: Payload; ordinal?: number; provenance: Provenance }` | `ordinal` is presentation-only and deliberately **not** hashed: PostgreSQL assigns physical order, and hashing it manufactures diffs between a declared schema and a live catalog that agree. |
| <a id="DependencyEdge"/> `DependencyEdge` | `{ from: StableId; to: StableId; kind: EdgeKind }` | Hierarchy is a view; the edge is the data. |
| <a id="EdgeKind"/> `EdgeKind` | `"depends" \| "owner" \| "memberOfExtension" \| "managedBy" \| "evaluates"` | `evaluates` is the kit's own addition — the edge `pg_depend` cannot give you, because it records a dependency on the enum *type*, not on an individual label. |
| <a id="Provenance"/> `Provenance` | `{ origin: Origin; ownership: Ownership; sourceRef?; extension? }` | Metadata, not state. It never enters a hash. |
| <a id="Origin"/> `Origin` | `"ts" \| "sql" \| "catalog" \| "extension" \| "baseline"` | Where a fact came from. |
| <a id="Ownership"/> `Ownership` | `"managed" \| "observed" \| "external"` | Whether the kit may write it. |
| <a id="CATALOG_PROVENANCE"/> `CATALOG_PROVENANCE` | `Provenance` | The stamp `extractCatalog` puts on everything it reads. |
| <a id="Payload"/> `Payload` | `{ readonly [k: string]: PayloadValue }` | The hashed half of a fact. Identity-free by construction. |
| <a id="Hash"/> `Hash` | `string` | Always spelled `sha256:<hex>`. |
| <a id="canonicalize"/> `canonicalize` | `(value: unknown) => string` | Deterministic JSON: keys sorted, `undefined` members dropped. Two fact bases with the same content serialise byte-identically. |
| <a id="contentHash"/> `contentHash` | `(payload: unknown) => Hash` | `sha256` of the canonical form. |
| <a id="sha256"/> `sha256` | `(text: string) => Hash` | The one hash function, so a spelling cannot drift. |

### Stable ids

| Name | Shape | What it is |
|---|---|---|
| <a id="StableId"/> `StableId` | a discriminated union over `FactKind`, e.g. `{ kind: "column"; schema; table; name }` | The identity tuple. `comment` carries its target as one already-encoded part, which is what lets one kind cover seven target kinds without seven arities. |
| <a id="FactKind"/> `FactKind` | `"schema" \| "table" \| "column" \| "default" \| "constraint" \| "index" \| "type" \| "enumLabel" \| "typeAttribute" \| "sequence" \| "comment" \| "extension"` | The twelve modelled kinds (Tier M). |
| <a id="encodeId"/> `encodeId` | `(id: StableId) => string` | `column:public.users.email`. The one and only encoding. |
| <a id="parseId"/> `parseId` | `(s: string) => StableId` | Its inverse. |
| <a id="idName"/> `idName` | `(id: StableId) => string` | The fact's own name — the part deliberately absent from the payload. |
| <a id="idSchema"/> `idSchema` | `(id: StableId) => string` | `""` for the two database-scoped kinds, because asking an extension for "its schema" is a category error and `""` is never a legal schema name. |
| <a id="parentOf"/> `parentOf` | `(id: StableId) => StableId \| undefined` | The structural parent, derived. |
| <a id="commentId"/> `commentId` | `(target: StableId) => StableId & { kind: "comment" }` | The comment fact that annotates a target, so nobody hand-builds the nesting. |
| <a id="defaultId"/> `defaultId` | `(column: StableId & { kind: "column" }) => StableId & { kind: "default" }` | A column's `DEFAULT` is its own fact, because `SET DEFAULT` is a catalog write and every other column change is a rewrite or a scan. |
| <a id="sameId"/> `sameId` | `(a: StableId, b: StableId) => boolean` | Structural equality without encoding both sides. |

### Payloads

Every payload is **identity-free**: grep for a field holding the fact's own name and you will not
find one. The exceptions that prove the rule are named in the source — a partition child records its
parent, and a type records its children's names, because from the parent's vantage point a child's
name *is* payload.

| Name | Shape | What it is |
|---|---|---|
| <a id="AnyPayload"/> `AnyPayload` | the union of the twelve below | What `Fact.payload` narrows to once you switch on `kind`. |
| <a id="SchemaPayload"/> `SchemaPayload` | `{ kind: "schema" }` | The discriminant and nothing else: a schema's identity is its name. |
| <a id="TablePayload"/> `TablePayload` | `{ relkind; persistence; rowSecurity; partitionStrategy; partitionKey; partitionOf; partitionBound; clusterOn }` | `clusterOn` lives on the table rather than the index because a clustered index is very often a constraint's backing index, which is not a fact of its own. |
| <a id="ColumnPayload"/> `ColumnPayload` | `{ type; notNull; notNullConstraint; notNullValidated; generationExpr; identity; generated; collation }` | `notNullConstraint` has three states, and the middle one — `%GENERATED%` — is what keeps the same fixture from diffing between PostgreSQL 17 and 18. |
| <a id="DefaultPayload"/> `DefaultPayload` | `{ expression }` | PostgreSQL's own spelling of the expression, never the kit's. |
| <a id="ConstraintPayload"/> `ConstraintPayload` | `{ contype; definition; validated; deferrable }` | `NOT VALID` is lifted out of the definition into `validated`, so validation state is an axis rather than a substring. |
| <a id="IndexPayload"/> `IndexPayload` | `{ definition; unique; valid }` | The definition with the index's own name replaced by `%ID%`. |
| <a id="TypePayload"/> `TypePayload` | `{ typtype; baseType; notNull; default; collation; checks }` | Enum, domain and composite in one kind, because all three have the identity tuple `[schema, name]` and `pg_type` is organised the same way. |
| <a id="TypeAttributePayload"/> `TypeAttributePayload` | `{ type; collation }` | `column` is to `table` as this is to `type`. |
| <a id="EnumLabelPayload"/> `EnumLabelPayload` | `{ kind: "enumLabel" }` | A label's identity is its text, which lives in the id; its position is the unhashed `ordinal`, so appending a value never perturbs its neighbours. |
| <a id="SequencePayload"/> `SequencePayload` | `{ dataType; start; increment; minValue; maxValue; cache; cycle; ownedBy }` | Bounds as strings, because `int8` bounds do not survive a `number`. |
| <a id="CommentPayload"/> `CommentPayload` | `{ text }` | Its own fact, so a re-worded comment does not look like an `ALTER TABLE`. |
| <a id="ExtensionPayload"/> `ExtensionPayload` | `{ schema }` | Declare-only: created if absent, **never dropped**. `extversion` is deliberately absent — a version is a property of the cluster, not of the schema in the repository. |

## Diff and delta

### `diffIR`

{/* docs: signature */}
```ts
function diffIR(current: SchemaIR, desired: SchemaIR, options?: DiffOptions): DiffResult
```

Compares two fact bases and returns the deltas, the renames that were accepted, the hints that were
rejected and why, and the current IR **after** the accepted hints were folded in — which is what the
plan is then built against. It never queries: `diagnostics` are threaded in from the extractor so
that `strictUnmodeled` has something to re-classify.

| Name | Shape | What it is |
|---|---|---|
| <a id="DiffOptions"/> `DiffOptions` | `{ renameHints?; strictUnmodeled?; diagnostics? }` | `strictUnmodeled` turns a non-empty Tier-U census from an `info` into an `error`, which `writePlan` then refuses. Off by default: a census is a report, and making it fatal would refuse any database with a `citext` cast in it. |
| <a id="DiffResult"/> `DiffResult` | `{ deltas; renames; rejectedHints; diagnostics; current }` | A rejected hint carries its reason, so a `renamedFrom` that did not fire says so. |
| <a id="Delta"/> `Delta` | `create \| drop \| alter \| rename \| addEnumValue`, discriminated on `op` | `addEnumValue` carries its ordering anchor, which is the fix for the enum-ordering bug the design calls out. |
| <a id="isEmptyDiff"/> `isEmptyDiff` | `(result: DiffResult) => boolean` | `migrate verify` semantics: two fact bases agree iff every fact **and every edge** agrees. |
| <a id="labelsOf"/> `labelsOf` | `(ir: SchemaIR, typeId: StableId) => string[]` | An enum's labels in ordinal order. |
| <a id="RenameHint"/> `RenameHint` | `{ from: StableId \| string; to: StableId \| string }` | Rename hints are an **input**. Nothing in the kit infers them. |
| <a id="RenameRecord"/> `RenameRecord` | `{ kind; from; to; source: "annotation" \| "cascade"; confidence: "unambiguous" }` | `cascade` is not inference: it is the auto-named constraint PostgreSQL declined to rename along with the table an annotation already renamed. |
| <a id="applyRenameHints"/> `applyRenameHints` | `(current: SchemaIR, desired: SchemaIR, hints: readonly RenameHint[]) => …` | A hint applies iff the old id exists on the current side and the new one does not. Anything else is rejected with a reason rather than guessed. |
| <a id="definitionsAgreeUnderRename"/> `definitionsAgreeUnderRename` | `(currentDef: string, desiredDef: string, renames) => boolean` | An identifier may differ **only** in the renamed direction; a definition that changed for any other reason still produces a real `alter`. |
| <a id="tokenizeDefinition"/> `tokenizeDefinition` | `(def: string) => Token[]` | Splits a stored definition into identifier tokens and everything else, through the lexer, so a `CHECK` body is never edited as if it were a name. |
| <a id="renameCandidates"/> `renameCandidates` | `(diff: DiffResult, desired: SchemaIR) => RenameCandidate[]` | The rename questions this diff raises, sorted so a CI envelope is stable. Anything an annotation already resolved is simply not here. |
| <a id="RenameCandidate"/> `RenameCandidate` | `{ kind; from; to; confidence; alternatives; reason }` | What `--interactive` shows and what exit code 2 is about. |
| <a id="RenameConfidence"/> `RenameConfidence` | `"unambiguous" \| "ambiguous" \| "nearMiss"` | Never an authority — only a prompt. |

## Statements, ordering and the plan

### `buildPlan`

{/* docs: signature */}
```ts
interface BuildPlanInput {
  readonly seq: number
  readonly name: string
  readonly statements: readonly Statement[]
  readonly segments: readonly Segment[]
  readonly fromFingerprint: string
  readonly toFingerprint: string
  readonly pgVersionNum: number
  readonly renames: readonly RenameRecord[]
  readonly diagnostics: readonly Diagnostic[]
  readonly schemas?: readonly string[]
  readonly proof?: Proof
  readonly acknowledge?: AcknowledgeInput
}

function buildPlan(input: BuildPlanInput): Plan
```

Stamps an ordered statement stream as a `.plan.json`: the two fingerprints, the managed schema set,
the transaction mode, the hazards with their acknowledgement state, and a `planId` that deliberately
**excludes** `generated` and `proof`, so the same logical plan re-proven by a different person on a
different day has the same id. Every statement gets `lock_timeout = 3s`; `statement_timeout` is
`30s` except on intentionally long builds (`shareUpdateExclusive`), which carry none.

### `writePlan`

{/* docs: signature */}
```ts
function writePlan(
  dir: string,
  plan: Plan,
  options?: { readonly allowUnproven?: boolean; readonly allowDataLoss?: boolean },
): Promise<{ sqlPath: string; planPath: string }>
```

Writes `NNNN_name.sql` and `NNNN_name.plan.json`, and refuses in three cases: the plan is not proven
(`ProofRequiredError`), it carries an unacknowledged destructive hazard
(`UnacknowledgedHazardError`), or the name would escape `dir` or overwrite a file
(`UnsafePlanPathError`). The refusal is the mitigation: an ordering bug becomes a `generate` failure
on a throwaway database instead of a production incident.

### `lintPlan`

{/* docs: signature */}
```ts
function lintPlan(plan: Plan, sqlText: string, options?: LintOptions): LintResult
```

Runs the hazard rules over a plan and the `.sql` beside it, applies the `-- pg-prime:nolint CODE
"reason"` directives found in the text, and returns findings with `acknowledged` and `suppressedBy`
already resolved. It needs no database, which is why `migrate lint <file>` runs without one. Every
code it can report is listed on [hazard codes](/pg-prime/reference/hazard-codes/).

### `hazardSeverity`

{/* docs: signature */}
```ts
function hazardSeverity(code: string): "error" | "warn"
```

## Proof

`generate` proves the plan before it writes it: clone, apply, re-extract, assert the diff against the
desired state is empty. See [proof](/pg-prime/concepts/proof/) for why that is worth the seconds it
costs.

### `proveOnShadowClone`

{/* docs: signature */}
```ts
function proveOnShadowClone(input: ProveInput): Promise<ProofResult>
```

`migrate verify` semantics, run at generate time: clone the source database, apply the plan's stages
in order, re-extract, and assert the diff against `desired` is empty. `cloneName` must start with
`pgprime_shadow_` — anything else raises `UnsafeCloneNameError`, because that prefix is the only
thing authorising this code to `DROP DATABASE … WITH (FORCE)`.

### `dumpSchema`

{/* docs: signature */}
```ts
function dumpSchema(req: DumpRequest): Promise<string>
```

A schema-only `pg_dump` of exactly the managed schemas, spawned as a subprocess with the password in
`PGPASSWORD` so it never lands in the process table. Each schema is passed as a **quoted pattern**:
unquoted, `--schema App` is case-folded and `*`, `?`, `.` and `[` are wildcards, which is how a
mixed-case schema once matched nothing and the oracle reported `skipped` while the plan sailed
through.

### `compareDumps`

{/* docs: signature */}
```ts
function compareDumps(cloneDump: string, desiredDump: string): DumpComparison
```

The independent witness. The shadow proof is self-referential — the kit's extractor, the kit's
differ, the kit's canonicaliser — so an attribute the extractor does not model is invisible to
*both* sides of the equality. `pg_dump` is PostgreSQL's own serialiser and shares no code with the
kit: if the clone and the desired database dump identically, every attribute PostgreSQL considers
part of the schema survived, including the ones the kit has never heard of. Multiset difference, so
a duplicated statement on one side is still a difference.

## History and locks

Every history object lives in one schema, `pgprime`: six tables and a version row. The lock is two
things at once — a session advisory lock, which is what actually excludes a second deploy, and a
`pgprime.lock` row with a heartbeat, which is what lets a human see *who* holds it.

### `ensureHistory`

{/* docs: signature */}
```ts
function ensureHistory(client: CatalogClient): Promise<void>
```

Creates the `pgprime` schema and its six tables, idempotently, **in its own transaction**. Its own
transaction matters twice: the statements must not half-land, and they must not sit inside the
caller's migration transaction, or a failed migration would roll the history schema away with it.
`IF NOT EXISTS` makes the sequence idempotent but not race-free — two sessions can both pass the
existence check and one then gets a `23505` — so it retries.

### `historyPresent`

{/* docs: signature */}
```ts
function historyPresent(client: CatalogClient): Promise<boolean>
```

Does `pgprime.migrations` exist? Read-only commands ask this instead of calling `ensureHistory`,
because `status` and `doctor` must not create a history schema as a side effect of being run.

### `acquireSessionLock`

{/* docs: signature */}
```ts
function acquireSessionLock(client: CatalogClient, database: string, schemas: readonly string[]): Promise<boolean>
```

`pg_try_advisory_lock` on a key **derived** from the database name and the managed schema set, so
two unrelated schema sets in one database do not serialise against each other. Session-scoped, which
means it must be taken on a dedicated, direct connection: under a transaction-mode pooler it is
silently broken, and `detectTransactionPooler` is the probe that says so.

### `releaseSessionLock`

{/* docs: signature */}
```ts
function releaseSessionLock(client: CatalogClient, database: string, schemas: readonly string[]): Promise<void>
```

The matching unlock. It computes the same key, so a caller cannot release a lock it did not take by
passing a different schema set.

### `inspectLease`

{/* docs: signature */}
```ts

```

Reads the `pgprime.lock` row and says whether it is stale. Staleness is computed **server-side**
from `heartbeat_at`, so a skewed client clock cannot invent a stale lease. This is what
`migrate unlock` prints before it offers to break anything.

### `forceUnlock`

{/* docs: signature */}

Deletes the lease row. It **cannot** release the winner's session advisory lock — only that
connection can, or its death — so breaking the lease of a deploy that is still running gets you a
second runner that immediately fails to acquire the advisory lock rather than two concurrent

## The runner

### `applyPending`

{/* docs: signature */}
```ts
function applyPending(conn: ConnInfo, migrationsDir: string, options?: ApplyPendingOptions): Promise<ApplyPendingResult>
```

The whole of `migrate apply`: open a dedicated connection, probe for a transaction pooler, ensure the
history schema, take the lease and the advisory lock, reconcile the directory against
`pgprime.migrations`, apply the pending files in `(seq, name)` order, run the repeatables pass, and
release. It never generates and never introspects the desired state — what runs is what is on disk.
The heartbeat is written from a **second** connection, because the migration connection can be
inside one `CREATE INDEX CONCURRENTLY` for minutes and `pg.Client` serialises.

```ts
import { applyPending, EXIT, type ConnInfo, type RunnerEvent } from '@pg-prime/kit'

const conn: ConnInfo = { host: '127.0.0.1', port: 5432, user: 'postgres', password: '', database: 'app' }

const result = await applyPending(conn, './migrations', {
  schemas: ['public'],
  onEvent: (event: RunnerEvent) => {
    if (event.kind === 'migration') console.log(`${event.id} ${event.state}`)
  },
})

if (result.exitCode !== EXIT.ok) throw new Error(result.error?.message ?? result.status)
```

### `applyPendingOn`

{/* docs: signature */}
```ts
function applyPendingOn(client: CatalogClient, migrationsDir: string, options?: ApplyPendingOptions): Promise<ApplyPendingResult>
```

The same run on a connection you own. The trade is explicit: you become responsible for the first

## Data migrations

Lane 2 of the migration model: a file tagged `-- pg-prime:batch`, whose every statement is
re-executed in its own transaction until it reports zero rows. See
[data migrations](/pg-prime/guides/data-migrations/).

### `runBatchStatement`

{/* docs: signature */}
```ts
function runBatchStatement(
  client: CatalogClient,
  sql: string,
  statement: number,
  state: Omit<DataProgress, 'updatedAt' | 'migrationId'>,
  options: BatchOptions,
): Promise<BatchOutcome>
```

Runs one statement of a batch file to completion. Each iteration is its own transaction:
`SET LOCAL pgprime.batch_size` and `SET LOCAL pgprime.watermark` through `set_config`, execute, read
`rows_done` and `watermark` off the statement's own result — falling back to the command tag when it
returns neither — write the progress row **inside that same transaction**, commit, sleep, repeat
until the statement reports zero rows. Because the work and the bookkeeping commit together, a
`SIGKILL` can neither lose a committed batch's watermark nor record one whose rows rolled back.
`state` is threaded in and out so a whole file's progress lives under one `data_progress` row, and
`STALL_LIMIT` iterations that report rows without moving the watermark raise `BatchStalledError`.

## SQL text

The kit has one lexer, and everything that reads SQL text goes through it. That is why a `--` inside
a dollar-quoted body is not a directive, why a `;` inside a string literal does not split a
statement, and why a `CHECK` body is never rewritten as if it were an identifier.

### `quoteIdent`

{/* docs: signature */}
```ts
function quoteIdent(name: string): string
```

Always quotes, and validates first: an empty name, a NUL byte, a lone surrogate or more than 63 UTF-8
bytes raises `InvalidIdentifierError` with the `problem` naming which. Always quoting is the point —
a conditional quoter has a branch where the condition is wrong.

### `quoteLiteral`

{/* docs: signature */}
```ts
function quoteLiteral(value: string): string
```

A single-quoted string literal with the quotes doubled. It is for DDL the kit emits, not for user
data at run time; the query builder in `pg-prime` binds parameters and never interpolates.

### `quoteQualified`

{/* docs: signature */}
```ts
function quoteQualified(schema: string, name: string): string
```

`"schema"."name"`, both halves validated. Every identifier the emitter writes is schema-qualified,
which is what lets the generated `.sql` set `search_path = pg_catalog` and still mean the same thing
under `psql` as it does under the runner.

|---|---|---|
