integrated on 2026-08-27. Each area below lists its findings, what happened to each, the files
that changed and the tests that pin the change. Section 8 is the part a reader of `02`, `03`, `05`
and `06` needs: **the contract changes**, i.e. what a caller can observe that moved.

## 7 Cross-area: the `nestNullable` witness (T2)

Held back from the concurrent pass because it spans the builder, the compiler and the type layer.

**The defect.** `makeGroup` picked the sentinel as the *first NOT NULL column ref in key order,
whatever its alias*. With `posts p` driving and `LEFT JOIN users u`,
`nestNullable({ pid: t.p.id, email: t.u.email })` chose `p.id` — a driving-side column, present on
every row the query can return — so the object was **never** null and `email: null` was typed
`string`. Swapping the two keys changed the answer, which means a caller's formatting decided
nullability.

**The fix.** The witnesses are chosen in the builder, which is the only layer that knows both
`joins[*].type === 'left'` and each `RefNode.alias`. `compileProjection` now takes the left-joined
alias set from `select.ts`, and `groupWitnesses` applies `03` §2.2's ladder:

1. left-joined members the schema declares NOT NULL;
2. failing that, **every** left-joined member (the all-null heuristic, narrowed to the columns the
   join can actually null, so a driving-side column no longer votes);
3. failing that, `[]` — **never null**, because nothing outer-joined contributes.

It uses `GroupPlan.witnesses`, the optional override C10 had already added, and it recurses, so a
group nested inside a group answers the same question about itself. `nest({...})` carries no
`witnesses` and its plan is byte-identical to before. `RETURNING` clauses and relation sub-selects
pass `NO_LEFT_JOINS` — neither can outer-join anything, so a `nestNullable` in one is never null.

Taking the join set at `.select(…)` time rather than at `toAst()` is sound for the joins this
builder can express: a projection can only reference aliases already in scope, and `innerJoin` /
`leftJoin` are the only two forms, so a later join can never turn an inner alias outer. A `RIGHT`
or `FULL` join would, which is a reason not to expose either without revisiting this.

**The type side.** `nestNullable`'s `| null` stays unconditional and is now documented as a
deliberate over-approximation: the type sees only the projection record, never the joins, and
closing the gap needs a fourth `Query` type parameter (`04` §1.3 rule 3). The two disagree only in
the safe direction — a needless null check, never a missed one.

**Tests.** `test/query/select.test.ts` — SQL goldens and decoder assertions for both key orders,
plus the inner-join "never null" case; `test/live-query/select.test.ts` — a real `LEFT JOIN`
through `_db.ts` against a `raw()` oracle, both key orders. All four were confirmed to fail
against the pre-fix witness choice.

**Known limitation, unchanged in kind but changed in outcome.** A nullable group spanning **two**
left-joined aliases has no single "did my row exist?" question. It used to be resolved by key
order; it is now resolved by ANDing every witness, so the object is null only when *both* joins
missed. `test/query/select.test.ts`'s `a group spanning TWO left-joined aliases…` pins that and
states the residue: one surviving join can still hand back an object with a null in a field the
schema declares NOT NULL. `03` §2.2's "AS BUILT" note describes the superseded single-sentinel
rule. **Open question for `03`:** whether such a group should be a named `BuilderError` instead.

## 8 Contract changes

What a reader of `02`, `03`, `05` and `06` needs to know moved. None of the other design docs were
edited in this pass; `03`'s Appendix A was **regenerated** by its own
`PGORM_UPDATE_DOCS=1 pnpm test -- appendix-a` generator, and the diff is one line (see below).

### 8.1 Driver (`02`)

- **`capabilities.cancel`** is `'pg_cancel_backend'` by default and `'protocol'` when
  `PgDriverConfig.createCancelClient` is supplied. That field is now typed
  `() => PgLikeCancelClient` (`cancel(client, query?)`), not `() => PgLikeClient`.
- **`maxRows`** is no longer `DECLARE`/`FETCH` but `Parse/Bind/Describe(P)/Execute(rows=n)/Close(P)/Sync`
  — one round trip, the real command tag and notices, `INSERT … RETURNING` supported. Closing a
  suspended portal **stops** a row-returning DML rather than truncating its output.
  `maxRows: 0` still runs the statement.
- **SQLSTATE 57014** is `'cancelled'` only when our `AbortSignal` fired or the backend said
  "due to user request"; `statement_timeout`/`lock_timeout` are `'timeout'`.
- **`release()` disposes on its own** when the connection is unusable, when a client-side timeout
  fired, or when `transactionStatus` is `'T'`/`'E'`.
- `PgLikeClient.removeListener` is now **required**; `PgLikeResult.command` is `string | null`;
  `PgDriverErrorData` gained an optional `cancelError`.
- `timeoutMs: 0` means "inherit the Pool's `query_timeout`" — pg reads it as falsy, so there is no
  per-query way to say "no deadline". The cancel spare-connection wait is a fixed 2 s; the escape
  hatch is `createCancelClient`.

### 8.2 Encoders and the registry (`02` §4)

- **A value with no codec is now a `PgEncodeError`, not a JSON string.** `unknownCodec.encode`
  refuses `undefined`, functions, symbols and plain objects, per §4.5's ban on the
  `JSON.stringify` fallback. A bare `${obj}` in a `sql` template therefore throws at compile
  instead of binding `'[object Object]'`-ish text. The tag's own invariant is unchanged — a hole
  is always data, never SQL; the value simply never reaches the wire.
- **`undefined` is never SQL NULL**: not as an array element, not in a template hole (that is an
  `InvalidFragmentError` naming the hole index), not in `jsonb`. `null` still binds.
- **`timestamptz` wire text changed spelling**: `2020-03-04 05:06:07.000Z`, not
  `2020-03-04T05:06:07.000Z`. Same instant, same OID, different bytes — `toISOString()`'s
  expanded-year form is rejected by the server outside years 1–9999. This is the only line that
  moved in `03` Appendix A: the §2.6 `timestamptz[]` param is now
  `["{click}","{\"2026-01-01 00:00:00.000Z\"}"]` (quoted because the element text contains a
  space; still a byte-for-byte round-tripping array literal).
- **Decoders are strict.** `bool` accepts exactly `'t'`/`'f'` at depth 0; integers require
  `/^[+-]?\d+$/` plus a safe-integer check; floats require a finite-decimal spelling
  (`NaN`/`±Infinity` still special-cased and still *encodable* — see the B12 deferral).
- **`timestamptz:string`** moved from `jsonEncode: 'native'` to `'text'`, so the compiler emits
  `::text` for it inside `json_build_object`.
- **New registered types**: `interval` (1186), `"char"` (18), `macaddr` (829), `macaddr8` (774),
  `bit` (1560), `varbit` (1562), `pg_lsn` (3220), each with its array codec. `interval` decodes
  both IntervalStyles and always encodes ISO-8601. `interval` is therefore no longer an unknown
  OID.
- **`Registry.clone()`** exists; **`Registry.onUnknownOid(handler)`** is a documented per-
  RowDescription debug hook on the class (not on the `CodecRegistry` interface).
- **Array codecs from `builtinCodecs()` are shared singletons** across every `Registry` (one
  `WeakMap` memo). Nothing mutates a codec in place today; `register({...codec})` spreads.

### 8.3 Query builder (`03`)

- **`.allRows()` is new and required.** An `UPDATE` or `DELETE` with no `.where()` is a named
  `BuilderError` at `toAst()` unless the caller opts in with `.allRows()`. `03` §2.5 has no
  unconditional-write example, so this is a new spelling the section should carry.
- **`onConflict().columns()` takes bare refs** — `c.columns(t => [t.email])`, not the destructured
  scope map §2.5 shows. The callback receives the target's `RefScope` directly, and a ref
  belonging to another table is a named error even when the column name matches.
- **The `unnest` bulk strategy cannot carry an array column.** `auto` falls back to `values`; an
  explicit `strategy: 'unnest'` is a named `BuilderError` (one array per column would need a
  `T[][]` parameter, which PostgreSQL has no type for, and `unnest` flattens every dimension
  anyway). `chunkSize` must be a positive integer.
- **`insertInto(t).fromSelect(q)` takes its column list from the sub-select's projection order**,
  because `INSERT … (cols) SELECT` is positional. `values()`/`valuesMany()` still use declaration
  order.
- **A registry is per `pgOrm()` instance.** `pgOrm({...})` with no `registry:` now builds a fresh
  `new Registry()` instead of sharing the process-wide `defaultRegistry()`, so an enum resolved by
  one instance is invisible to another. Pass `registry:` explicitly to share.
- **`UPDATE … FROM` / `DELETE … USING` with RETURNING emits fully qualified columns**
  (`returning "products"."id" as "id"`). A bare `id` there resolves against the target *and* every
  FROM item — still 42702 on a real server. Plain `INSERT`/`UPDATE`/`DELETE` RETURNING is
  byte-identical to before, so the §2.5 goldens stand.
- **A `one()` relation may not carry its own `limit`/`offset`** — `UnsupportedNodeError` naming the
  relation, because the `LEFT JOIN LATERAL` would return *n* rows and duplicate the parent.
- New named errors throughout: alias collisions (`using`, `fromValues`, a second `.set()` on the
  same column, a user alias shaped like the compiler's reserved `_r\d+`), `__proto__` as a
  projection / insert / SET key, `asScalar()` on a group, `.compile()` with no projection, a
  non-expression handed to `and`/`or`/`not`/`desc`/`fn.*`, and a NULL right operand to any ordered
  comparison (not just `eq`/`neq`).
- `exists`/`notExists`/`inQuery` take `QuerySource`; `union`/`fromSelect` take the branded
  `SelectSource<O>`. Both reject an insert/update/delete; `QuerySource` additionally admits a
  hand-built node from `src/compile/nodes.ts`, which is why the two spellings coexist.
- `case`, `row` and `array` now **emit** (they were declared-not-implemented), with constructors
  `caseWhen` / `rowExpr` / `arrayExpr`.
- `DecodePlanError` (code `DECODE_PLAN`) is a new exported error class.
- `src/index.ts` is a new curated public barrel. **`packages/pgorm/package.json` still does not
  point at it** — there is no build yet, so `import 'pgormjs'` resolves to nothing (deferred).

### 8.4 Schema (`05`)

- `RelConfig.from` / `.to` are **required** at the type level, matching a runtime that always threw
  without them.
- Contradictory column chains (`nullable` after `pk`/`ro`, `default`/`defaultSql`/`$default` after
  `ro`) are compile errors; `pgEnum` throws on a duplicate label.
- Identifier validity, duplicate DB column names and relation column-type mismatches are all
  `SchemaError`s **at declaration time**, naming the declaration, instead of an anonymous
  `sql.ident` failure at first compile.
- `DateString` is `PgDateString`; there is one date brand.
- `src/schema` now imports `../sql/errors.js` and `../sql/ident.js`, so it is no longer standalone.
  If it is meant to be importable on its own, `SchemaError` and `quoteIdentPart` belong in a lower
  layer.

### 8.5 Migration kit (`06`)

- **Provisioning is a ladder** (`§3.2`, now implemented in `prove.ts`): `CREATE DATABASE … TEMPLATE`
  first, and on 55006 an empty `pgorm_shadow_*` database into which the current IR is materialised
  through our own emitter. The tier used is recorded as `proof.provisioning` — the materialised
  tier is a slightly weaker starting point than a byte copy, and that is now visible in the plan.
  **`generate()` no longer terminates sessions on the live target.**
- **The `§3.6` acknowledgement gate is implemented.** `.plan.json` gains an `acknowledged` field
  (`dataLoss` subjects, `by`, `reason`, `at`, `blanket`), deliberately excluded from `planId` like
  `generated`, because it carries a timestamp. `writePlan` refuses any plan with an unacknowledged
  error-severity hazard unless `allowDataLoss`.
- `RenameRecord.source` admits `"cascade"` for auto-named constraints and indexes paired
  unambiguously behind an annotation-driven rename.
- `SchemaIR.toJSON(pgMajor)` is renamed **`toCheckpoint(pgMajor)`**; `IndexPayload.primary` is
  gone; `Diagnostic` gained a structural `count`.
- Partitioned parents, partitions and both ends of a `pg_inherits` row are **excluded and
  reported** as an error-severity `unsupported_kind`, not silently flattened.
- New error classes: `UnsafeDatabaseNameError`, `UnsafeCloneNameError`, `InvalidMigrationIdError`,
  `UnsafePlanPathError`, `UnacknowledgedHazardError`, and the abstract `WriteRefusedError` they
  share. `generate()` catches only `WriteRefusedError`; an `EACCES`/`ENOSPC`/`ENOTDIR` now
  propagates instead of being reported as `writeRefusal`.
- `packages/pgorm-kit/src/sql/ident.ts` is a deliberate **port** of `packages/pgorm/src/sql/ident.ts`
  (the kit cannot import pgormjs — no entry point or build yet). Two places to keep in sync.

## 9 Integration notes

Fixed while integrating, beyond applying the areas' cross-area requests:

- **`test/driver/maxrows.test.ts` was not idempotent against a persistent server.** Its

  outlived the session; a second `PGORM_TEST_URL` run failed the hook with
  `42723 function "cap_notice" already exists`, which in turn cascaded into a spurious
  `transactionStatus tracks I → T → E → I` failure in `execute.test.ts`. The two temp tables beside

  twice back to back to prove idempotency: 1314/1314 both times.
- **`NullOperandError`'s rendered symbol** was hard-coded to `'<>'`/`'='`. It is now thrown by

  from an operator→symbol map. The class and its stable `NULL_OPERAND` code are unchanged.
- **`Query.window` / `GroupedQuery.window`** accept `WindowSpec | WindowLiteral | WindowFn`. The
  runtime (D10) and the module docblock already documented the callback spelling, but a function is
  not assignable to the all-optional `WindowLiteral` (weak-type detection), so
  `.window('w', t => w => …)` was TS2345.
- **The type-error message aliases live in `src/query/errors.ts`**, its documented home:

  `Selected<>` / `SetResult`. They are template-literal *string* aliases, never
  `OrmTypeError<…>` aliases — `errors.ts`'s header measures why. `type-errors:check` confirms the
  rendered goldens are byte-identical.
- **`03` Appendix A regenerated** through its own generator; one line changed (§8.2).
- Two areas reported the same defect with different prescriptions and were unified:
  `exists`/`inQuery` on `QuerySource` rather than `SelectSource` (documented in `nominal.ts`), and
  the `select.test.ts` / `relations.test.ts` `@ts-expect-error` requests, which the query owner had
